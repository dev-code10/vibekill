# VibeKill

### 바이브코딩의 위험성 — 프롬프트 한 줄로 다 된다고?

> **AI가 만든 웹사이트는 정상적으로 작동한다는 이유만으로 안전하다고 할 수 있을까?**

**VibeKill**은 자연어 프롬프트 한 줄로 생성한 커뮤니티 웹 애플리케이션을 대상으로 인증, 접근 제어, 세션 관리 등의 보안 문제를 직접 검증하고 기록하는 연구 프로젝트입니다.

본 프로젝트의 목적은 특정 AI 모델을 비난하거나 모든 바이브코딩 결과물을 위험하다고 일반화하는 것이 아닙니다. AI가 생성한 코드도 일반적인 소프트웨어와 마찬가지로 **검토, 테스트, 보안 검증이 필요하다**는 점을 실제 사례로 보여주고자 했습니다.

## 연구 대상 및 자료

```text
vibekill/
├── moru-community/  # 연구 대상 커뮤니티 웹 애플리케이션 소스코드
├── report/          # 보안 분석 보고서 및 취약점 검증 자료
└── README.md        # 프로젝트 소개
```

- **[`/moru-community`](./moru-community/)**: 바이브코딩으로 생성된 MORU 커뮤니티 웹 애플리케이션의 소스코드입니다. 연구자는 이 코드를 대상으로 동작 및 보안 검증을 수행했습니다.
- **[`/report`](./report/)**: 취약점 분석 내용, 검증 과정과 결과 등 연구 자료를 정리한 디렉터리입니다.

## 주요 검증 결과

다음은 카드뉴스에 소개한 대표 사례입니다. 상세한 테스트 조건과 나머지 점검 항목은 [`/report`](./report/)에서 확인할 수 있습니다.

검증 항목 | 확인된 현상 |
--- | --- |
비밀번호 72바이트 절단 | UTF-8 기준 첫 72바이트가 동일한 서로 다른 비밀번호로 같은 계정에 로그인 가능 |
계정 정지 해제 후 기존 세션 재사용 | 정지 중 사용하지 않아 폐기되지 않은 세션이 계정 재활성화 후 다시 인증에 사용됨 |
공지 게시글 수정 권한 검증 누락 | 일반 작성자가 자신이 작성하고 관리자가 공지로 지정한 글을 일반 게시글로 변경하면서 수정 가능 |

### 비밀번호 절단으로 인한 인증 검증 문제

회원가입 단계에서는 비밀번호의 JavaScript 문자열 길이를 검사하지만, 사용 중인 `bcryptjs`는 비밀번호의 **앞 72바이트**만 해싱 및 비교에 사용합니다. 따라서 한글처럼 UTF-8에서 여러 바이트를 차지하는 문자를 사용하면 화면에서 서로 달라 보이는 비밀번호라도 실제 검증에 사용되는 부분이 같아질 수 있습니다.

- **관련 코드:** `server.js` 회원가입 및 로그인 처리
- **검증:** 앞 72바이트가 같은 서로 다른 비밀번호로 로그인 성공 확인
- **영향:** 비밀번호 뒤쪽의 변경 사항이 인증에 반영되지 않을 수 있음

### 계정 정지 해제 후 기존 세션 재사용

관리자가 계정을 정지할 때 사용자 상태값(`is_active`)만 변경하며, 해당 계정의 모든 로그인 세션을 일괄 무효화하지 않습니다. 정지 중 인증 요청을 보낸 세션은 폐기되지만, **정지 중 사용하지 않은 다른 세션**은 계정 재활성화 이후 재로그인 없이 다시 사용할 수 있었습니다.

- **관련 코드:** `server.js` 인증 미들웨어 및 관리자 계정 상태 변경 API
- **검증:** 정지 중 세션 A는 `401`, 정지 해제 후 미사용 세션 B는 `200` 확인
- **영향:** 계정 정지와 복구만으로 기존의 모든 세션이 폐기되었다고 보장할 수 없음

> **주의:** 계정이 정지된 상태에서 인증을 우회했다는 의미는 아닙니다.

### 공지 게시글 수정 권한 검증 누락

서버는 게시글을 수정할 때 **기존 카테고리가 공지인지** 확인하지 않고, 요청에 포함된 **변경 후 카테고리**가 공지인지 여부만 확인합니다. 일반 사용자가 작성한 글을 관리자가 공지로 지정한 뒤에도, 해당 작성자는 카테고리를 `자유`로 변경하는 수정 요청을 보낼 수 있었습니다.

- **관련 엔드포인트:** `PATCH /api/posts/:id`
- **검증:** 공지 상태 유지 요청 `403`, 일반 카테고리로 변경하는 요청 `200` 확인
- **영향:** 관리자만 공지 상태를 관리해야 한다는 정책을 전제로 할 경우 공지 관리 권한이 일관되게 적용되지 않음

> **범위:** 다른 사용자가 작성한 모든 공지를 수정할 수 있다는 뜻은 아닙니다.

## 연구 방법

연구 대상 웹 애플리케이션을 직접 실행하고, 소스코드 검토와 브라우저 개발자 도구 및 HTTP 요청을 통한 동작 검증을 수행했습니다. 요청·응답 상태, 서버 처리 로직, 실제 데이터 변경 여부를 비교하여 재현 가능한 결과를 기록했습니다.

단순 기능 오류, 보안 설정 문제, 조건부 위험, 실제 재현된 취약점은 서로 구분해 평가했습니다. 코드가 작동한다는 사실과 충분한 보안성이 확보되었다는 사실은 다르다는 점에 주목했습니다.

## 연구 범위 및 한계

- 본 연구는 **프롬프트 한 줄로 생성한 특정 웹 애플리케이션 한 개**를 대상으로 합니다.
- 웹 애플리케이션 생성 이후 연구 대상으로 삼은 소스코드를 직접 수정하지 않고 검증했습니다.
- 본문에 소개된 결과는 각 항목의 **재현 조건과 테스트 환경**에 한정됩니다.
- 모든 AI 모델과 바이브코딩 도구에서 동일한 문제가 발생한다고 주장하지 않습니다.
- 점검을 수행했다고 해서 모든 보안 취약점을 발견했거나 서비스 전체의 안전성을 보증하는 것은 아닙니다.

## 소스코드 공개 안내

본 저장소의 웹 애플리케이션 소스코드와 연구 결과는 검증 과정의 투명성을 높이고 보안에 대한 경각심을 공유하기 위해 공개합니다. 공개된 코드가 실제 운영 서비스에 적합하거나 안전하다는 뜻은 아닙니다. 배포 또는 활용하려면 별도의 보안 검토와 수정이 필요합니다.

분석 및 재현은 권한이 있는 시스템이나 별도의 테스트 환경에서만 수행해야 합니다.
