# 계정 정지 해제 후 기존 세션 재사용

계정을 정지한 뒤 다시 활성화하면 정지 전에 발급된 일부 세션이 다시 인증에 사용됐다. 정지 중 요청을 보낸 세션은 폐기됐지만, 사용하지 않고 보관한 세션은 남아 있었다.

## 재현 조건

같은 일반 계정의 서로 다른 세션 두 개와 계정 상태를 변경할 관리자가 필요하다. 정지 중 한 세션은 인증 요청을 보내고, 다른 세션은 사용하지 않는다. 이후 세션 유효기간 안에 계정을 다시 활성화한다.

이 문제는 기존 세션을 가진 상태에서 발생한다. 세션 탈취 자체를 재현한 것은 아니다.

## 검증 과정과 결과

회원가입으로 발급된 세션을 A, 별도 로그인으로 발급된 세션을 B로 구분했다. 서로 다른 쿠키인지 확인하고 각각 `GET /api/me`를 호출해 동일한 일반 계정으로 인증되는지 확인했다. 검증 계정의 ID는 `3`이었다.

관리자는 다음 요청으로 계정을 정지했다.

```http
PATCH /api/admin/users/3/status
Content-Type: application/json

{"isActive": false}
```

응답은 `200`이었다. 이어서 A로 `/api/me`를 호출하자 `401`이 반환됐다. 정지 중 같은 계정의 비밀번호로 새 로그인을 시도해도 `401`이었다. 이 구간에서는 B를 사용하지 않았다.

관리자가 같은 경로에 `{"isActive": true}`를 보내 정지를 해제한 뒤, 정지 전에 보관한 A와 B의 쿠키를 각각 다시 전송했다. A는 `401`, B는 `200`이었다. B 응답에는 같은 사용자 ID `3`이 포함됐고 추가 로그인은 하지 않았다.

| 시점 | 세션 A | 세션 B | 새 로그인 |
| --- | --- | --- | --- |
| 정지 전 | `200` | `200` | B 발급 시 `200` |
| 정지 중 | `401` | 요청하지 않음 | `401` |
| 정지 해제 후 | `401` | `200` | 요청하지 않음 |

표의 A와 B 결과는 `GET /api/me`의 응답이다. 정지 해제 후에는 쿠키 저장소의 현재 값에 의존하지 않고, 미리 보관한 원래 쿠키를 재전송했다. [요청과 응답 기록](evidence/2026-10-13/session-reactivation.json) · [검증 코드](poc/session-reactivation.mjs)

## 원인

관리자 계정 상태 변경 API는 [server.js 626행](https://github.com/dev-code10/vibekill/blob/9fda842dda38a933034159e539ea7544c67615ac/moru-community/server.js#L626)에서 사용자 상태만 갱신한다.

```javascript
await pool.execute(
  'UPDATE users SET is_active = ? WHERE id = ?',
  [isActive ? 1 : 0, id],
);
```

이때 해당 사용자의 세션을 일괄 폐기하는 처리는 없다. 세션 폐기는 [인증 미들웨어 158행](https://github.com/dev-code10/vibekill/blob/9fda842dda38a933034159e539ea7544c67615ac/moru-community/server.js#L158)에서 비활성 계정의 요청이 들어왔을 때 수행된다.

```javascript
if (!user || !user.is_active) {
  req.session.destroy(() => {});
  return res.status(401).json({
    error: '계정이 비활성화되었거나 로그인이 만료되었습니다.',
  });
}
```

`req.session.destroy()`는 현재 요청의 세션을 폐기한다. [Express의 Session.destroy 설명](https://expressjs.com/en/resources/middleware/session/#sessiondestroycallback)도 이 동작을 다룬다. A는 이 분기를 거쳤지만 B는 요청 자체가 없어 폐기되지 않았다. 계정이 다시 활성화되면 B는 같은 검사에서 통과한다.

## 영향

계정 정지를 세션 유출 대응 수단으로 사용하는 경우 문제가 된다. 기존 세션을 가진 사람이 정지 중에는 요청을 보내지 않고 기다리면, 계정 복구 후 비밀번호를 다시 입력하지 않고 접근할 수 있다.

계정이 정지된 동안 인증을 우회한 결과는 아니다. 정지 중 A의 인증 요청과 새 로그인은 모두 차단됐다. 또한 세션이 이미 만료되거나 별도로 폐기된 경우까지 다시 살아나는 것은 아니다. 이번 재현은 만료 전의 유효한 세션으로 짧은 시간 안에 진행했다.

## 수정 방향

정지 또는 보안상 강제 로그아웃을 처리할 때 계정 단위로 기존 세션을 무효화해야 한다. 사용자와 세션의 연결을 관리해 해당 계정의 세션을 모두 삭제하거나, 계정별 세션 버전을 두고 이전 버전의 세션을 거부하는 방식으로 구현할 수 있다.

세션 버전을 사용한다면 로그인 시 현재 버전을 세션에 저장하고 인증 요청마다 사용자 레코드의 버전과 비교한다. 정지 시 `is_active` 변경과 버전 증가를 함께 처리하고, 정지 해제 시 이전 버전으로 되돌리지 않는다. 로그인과 정지가 동시에 진행되는 경우도 고려해야 한다.

수정 후에는 이번 절차에서 정지 해제 뒤 A와 B가 모두 `401`이어야 한다. 그 상태에서 새 로그인만 성공하고, 새로 발급된 세션은 정상적으로 사용할 수 있어야 한다.
